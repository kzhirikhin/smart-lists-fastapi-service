# Инструкции для ИИ-агентов

Этот файл действует для всего репозитория. Его цель — хранить короткие
обязательные правила работы. Актуальное состояние, границы безопасности и
устройство сервиса описаны в `PROJECT_MEMORY.md`.

## Перед началом работы

1. Прочитай `PROJECT_MEMORY.md`.
2. Проверь `git status` и не перезаписывай несвязанные пользовательские
   изменения.
3. Сверяй документацию с кодом. При расхождении источниками истины являются
   `requirements.txt`, `Dockerfile`, `.github/workflows/` и актуальные исходники
   в `app/`.
4. Перед изменением AI-потока изучи его целиком:
   `app/models/insights.py` → `app/routers/insights.py` →
   `app/services/ai.py` → обработчики в `app/main.py` → тесты.
5. Если меняется контракт с web-приложением, проверь соответствующий
   `src/app/actions/insights.ts` в репозитории `smart-lists`.
6. Модель угроз обоих компонентов живёт в `THREAT_MODEL.md` репозитория
   `smart-lists`; этот сервис разобран там как отдельный элемент. Меняя
   авторизацию, лимиты, логирование, состав payload или вызов Anthropic,
   сверься с ней и обнови её в той же задаче.

## Архитектурные правила

- Это внутренний service-to-service API, а не пользовательский backend.
  `POST /insights` принимает только вызовы доверенного Smart Lists server.
- `GET /health` остаётся минимальным публичным liveness endpoint. Не добавляй
  туда проверки Anthropic, секретов или других внешних зависимостей без
  осознанного изменения эксплуатационного контракта.
- Пользовательская авторизация, доступ к списку и суточная квота принадлежат
  web-приложению. Этот сервис независимо проверяет Google ID-токен вызывающего,
  форму и бюджеты payload и применяет защитный per-IP rate limit.
- Не ослабляй проверку входящего токена: подпись, `aud` и `email` проверяются
  все три, и любая ошибка означает отказ. Токен вызывающего выпускается только
  на сервере и не должен попадать в клиентский код.
- Все недоверенные данные валидируй Pydantic-моделями на границе API.
  Клиентские лимиты считаются только первой линией защиты и не заменяют
  серверные.
- Сохраняй согласованность одиночных и совокупных бюджетов: длины полей,
  количество элементов и групп, максимум заметок и суммарную длину заметок.
- Не доверяй клиентским производным значениям, если их можно вычислить из
  проверенного payload. Так `list_note_included` и `included_item_notes`
  пересчитываются сервисом; только число намеренно опущенных заметок приходит
  от вызывающей стороны.
- Сетевой вызов Anthropic остаётся асинхронным, имеет конечный timeout и
  ограничение `max_tokens`. Не добавляй бесконтрольные повторы: они увеличивают
  стоимость и могут продублировать запрос.
- Vendor-specific ошибки не должны раскрывать вызывающей стороне секреты,
  prompt или внутренние детали.

## Безопасность prompt

- Считай недоверенными `title`, `groups`, `list_note`, `items[*].name`,
  `items[*].note` и `user_message`.
- Передавай пользовательские данные структурированным JSON, отдельно от
  system prompt. Не собирай prompt конкатенацией произвольных инструкций
  пользователя.
- Сохраняй единственный маркированный блок `<untrusted_user_data_json>`.
  Экранируй символы, позволяющие пользовательскому тексту закрыть служебный
  тег.
- System prompt должен явно запрещать исполнять команды из payload и раскрывать
  системные инструкции.
- Защита prompt снижает риск, но не делает ответ модели доверенным. Не добавляй
  исполнение кода, HTML или команд из ответа.
- Любое изменение сериализации, границы недоверенных данных или system prompt
  сопровождай тестом на попытку prompt injection.

## Лимиты, proxy и логирование

- Сохраняй ранний лимит объявленного размера тела и Pydantic-лимиты содержимого.
  Если потребуется строгий byte-level предел для chunked body, реализуй
  потоковое ограничение отдельно и зафиксируй новое поведение в документации.
- Текущий SlowAPI limiter хранит состояние в памяти процесса. Не описывай его
  как глобальную или пользовательскую квоту.
- Первый `X-Forwarded-For` считается доверенным только за контролируемым proxy.
  При изменении схемы ingress сначала определи доверенную цепочку proxy, затем
  меняй извлечение IP.
- Не логируй Bearer header, API-ключи, title, имена записей, заметки,
  `user_message`, полный prompt или ответ AI.
- Для продуктовой диагностики предпочитай размеры, счётчики, булевы признаки,
  HTTP-статус и длительность.
- `/health` намеренно не засоряет access log.

## Код и стиль

- Целевая версия Python — 3.13; она должна совпадать в `Dockerfile` и GitHub
  Actions.
- Используй современные type hints и конкретные типы. Не добавляй
  необоснованные `Any` и `# type: ignore`.
- Классы называй в PascalCase, функции и переменные — в snake_case,
  константы — в UPPER_SNAKE_CASE.
- Разделяй Pydantic-контракт, HTTP-слой и интеграцию с Anthropic по существующим
  модулям. Не переноси формирование prompt в router.
- Комментарии и проектную документацию пиши на русском. Объясняй причины и
  ограничения, а не синтаксис.
- Единственное исключение — `README.md`: он ведётся на английском как публичное
  описание проекта. Меняя его, сохраняй английский и не смешивай языки внутри
  файла.
- Все текстовые файлы сохраняй с LF согласно `.gitattributes`.

## Конфигурация и секреты

- Настройки читаются через `pydantic-settings`. Новую обязательную переменную
  добавляй в `Settings`, README, `PROJECT_MEMORY.md`, тестовое окружение CI и
  эксплуатационную конфигурацию.
- `.env` предназначен только для локальной разработки и не должен попадать в
  Git или Docker image.
- У сервиса нет production-секретов: вся конфигурация состоит из несекретных
  идентификаторов и адресов. Это состояние достигнуто намеренно — не вводи
  новый долгоживущий секрет, не обсудив альтернативу. Для Anthropic такой
  альтернативой стала workload identity federation, для вызывающего — Google
  ID-токен.
- Если секрет всё же появится, он живёт только в runtime-конфигурации Cloud
  Run. Не добавляй его в workflow, тесты, Bruno collection, Docker Compose или
  документацию.
- Для тестов используй очевидно нерабочие placeholder-значения. Anthropic в
  автоматических тестах должен быть замокан.
- `DEBUG` в production остаётся `false`; включение публикует `/docs` и
  `/redoc`.

## Зависимости

- Точные версии закреплены в `requirements.txt`. Меняй их намеренно, проверяя
  совместимость FastAPI, Starlette, Pydantic, httpx и TestClient.
- Не обновляй `requirements.txt` слепым `pip freeze` из окружения с
  посторонними пакетами.
- После изменения зависимостей создай чистое окружение или контейнер,
  установи `requirements.txt` и прогони все тесты.
- Версия Python в CI и production image должна оставаться одинаковой.

## Проверка изменений

**Политика тестирования обязательна.**

- Изменение поведения без актуального автоматического теста считается
  незавершённым.
- Минимальная проверка для любой правки кода — `pytest tests/ -v`.
- Меняя авторизацию, добавляй позитивные и негативные проверки заголовка.
- Меняя Pydantic-модели, проверяй обе стороны каждой границы и совокупные
  бюджеты.
- Меняя prompt, проверяй точную структуру вызова Anthropic, сохранность связей
  записи с её заметкой и статусом, а также невозможность закрыть untrusted-блок
  пользовательским текстом.
- Меняя middleware или limiter, добавляй тесты на статус, побочные эффекты и
  порядок выполнения.
- Тесты не должны обращаться к реальному Anthropic API, требовать production
  secrets или зависеть от сети.
- При изменении Dockerfile дополнительно собери image, если Docker доступен.
- При изменении deployment workflow проверь permissions, OIDC-аутентификацию,
  test gate и деплой SHA-tagged image. Не заменяй Workload Identity Federation
  долгоживущим JSON-ключом.
- Не меняй service account, под которым работает сервис, не изменив правило
  федерации в консоли Anthropic: правило привязано к `sub` и `email` этой
  личности, и смена личности выглядит как отказ Anthropic без видимой причины.
- Перед commit и push прогони релевантные проверки и не отправляй заведомо
  падающее или непроверенное изменение.
- Проверь итоговый diff на секреты, пользовательские данные, артефакты,
  случайные изменения dependency-файлов и несвязанные правки.

## CI и deployment

- `ci.yml` ничего не деплоит и не получает production credentials.
- `deploy.yml` запускается только для `main`; deploy зависит от успешного test
  job.
- GitHub token по умолчанию сохраняет `contents: read`; `id-token: write`
  выдаётся только deploy job.
- Gitleaks проверяет полную историю и печатает найденное только с `--redact`.
- Production revision разворачивается по immutable SHA tag. `latest` не
  используй как единственный идентификатор выкладки.
- Не меняй Cloud Run project, region, service, Artifact Registry или identity
  provider без явного согласования и обновления `PROJECT_MEMORY.md`.

## Обновление проектной памяти

Обновляй `PROJECT_MEMORY.md` в той же задаче, если изменились:

- API-маршруты, request/response contract или лимиты;
- модель безопасности, proxy assumptions, логирование или обработка ошибок;
- Anthropic model, prompt, timeout, output budget или внешний сервис;
- зависимости, Python version, команды или переменные окружения;
- CI/CD, container image, Cloud Run deployment или известное ограничение;
- важное принятое решение и его компромисс.

Не записывай туда пошаговую историю работы, временные отладочные детали,
предположения, секреты и содержимое пользовательских запросов. Обновляй дату
снимка и сохраняй файл компактным.
